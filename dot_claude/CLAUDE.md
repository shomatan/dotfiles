# CLAUDE.md (User-level)

## 言語設定

- 日本語でコミュニケーションを行うことを優先してください
- コードコメントやドキュメントも日本語で記述してください (国際的なプロジェクトを除く)

### 日本語の表記

- 日本語と半角英数字の間に空白を入れない。「直近5件」「15行」「0.5人日」「Phase1」と書き、「直近 5 件」「Phase 1」と書かない。固有名詞や製品名に空白が含まれる場合だけ原文どおりにする
- コロンは半角コロンと半角スペースにする。`<見出し>：<本文>` ではなく `<見出し>: <本文>` と書く
- 括弧は半角にし、開き括弧の前と閉じ括弧の後ろに半角スペースを置く。直後が句読点か行末なら後ろのスペースは要らない
- 対象は地の文、見出し、箇条書き。句読点「、。」と鉤括弧「」は対象外
- コードブロック、コマンド、ログ、URL、引用した原文、外部から与えられた文字列は書き換えない
- 上記はJira、Confluence、Slack、チャット返答、ドキュメントのすべてに適用する
- スキル (japanese-tech-writing など) が全角コロンや空白を指示していても、この節を優先する

## コーディングスタイル

- 簡潔で読みやすいコードを心がける
- 適切なエラーハンドリングを実装する
- コミットメッセージは日本語で記述する

## 設計の決定と文書

- **設計の決定の正本は ADR だけにする。** 同じ決定を別の設計文書 (Linear など) に持たない。
  二重に持つと、あとから読んだときに食い違う。要件は要件定義書、設計の決定は ADR と分ける
- コードのコメントや PR の本文から、ADR の外の設計文書を参照しない。根拠を指すなら ADR の節 (`ADR-NNNN D-n`) を指す
- **スタック PR では、ADR の変更を ADR を追加した最下段の PR に集める。** 上の PR で決定が変わっても、
  ADR は最下段で直して rebase で上へ伝える。上の PR では ADR を触らない
- 周辺の docs (コードの地図など) は、決定の水準の記述を最下段に書き、ファイルの場所はそのコードが入る PR で書く

### チケット番号

- ADR の冒頭の関連チケットの欄には書く (要件と議論への入口)
- ADR の本文、docs の地図、コードのコメントには原則書かない。書くのは、番号を開くと文書に無い情報が得られるときだけ:
  - まだ終わっていない作業 (「削除は別の変更で行う (<チケット>)」)
  - 文書の外にある仕様 (「失敗画面は <チケット> の仕様に合わせる」)
- 経緯のラベル (「<チケット> で決めた」「<チケット> の当初の案」) としては書かない。経緯はコミットの本文に書く

## 環境

- **環境は複数ある。環境依存のコマンドを書く前に `uname -s` で確かめる**
  (Ark が動いている機械は Linux。`brew` / `pbcopy` / BSD `sed` はそこで壊れる)
- Homebrewでパッケージ管理
- miseでツールバージョン管理
- zsh + Powerlevel10kを使用

## Git/GitHub設定

- コミットメッセージにCo-Authored-Byを追加しないこと
- プルリクエストに「Generated with Claude Code」のような生成した証跡を残さないこと

## 実行の担当

- **ユーザーにコマンドを実行させない。** `! <command>` を提示する前に、自分で実行しきる手段を最後まで探す。「対話的だから無理」は理由にならない
- **ブラウザ認証 (OAuth) も自分で完結させる**
  - CLI が loopback callback サーバを立てる型なら、バックグラウンド実行して標準出力から認可 URL を取り出す。callback は自分が立てたサーバが受け取る
  - 既存のブラウザプロファイル (`~/.config/chromium` など) に Google 等のログインセッションが残っていることが多い。`sqlite3 <profile>/Default/Cookies "select distinct host_key from cookies where host_key like '%<domain>%'"` で在否を確認できる
  - Playwright の `launchPersistentContext` にそのプロファイルを渡し、`executablePath` へ `~/.cache/ms-playwright/chromium-*/chrome-linux/chrome` を明示、`args: ['--password-store=basic']` を付けて headless 起動する。アカウント選択と同意画面は自分でクリックする
  - パッケージ版 Playwright とインストール済みブラウザのバージョンがずれて `Executable doesn't exist` が出たら、`npx playwright install` ではなく `executablePath` で既存ビルドを指す
- ユーザーに依頼してよいのは、**物理操作** (ハードウェアキー、カード読み取り、電話) と、**本人しか知らない秘密情報の入力**だけ。それ以外は自分でやる
- トークン失効 (`invalid_grant`) は再認証すれば直る。ユーザーに投げ返さず、その場で通す

## ユーザー確認

- ユーザーへの確認は必ず `AskUserQuestion` ツールを使用し、選択式で提示すること
- テキストで選択肢を羅列して確認を求めてはならない
- 選択肢は2〜4個に絞り、明確な説明を付けること

## メモリの書き方

メモリは最初は効くが、**古くなると誤った方向へ引っ張る**。
実際に起きた事故は 2 つの型に分かれた。

- **ファイル名が本文と正反対** (本文だけ更新され、名前が古い主張を持ち続けた)
- **結論は正しいが理由が誤り** (理由を信じた側が別の対処をして混乱した)

腐敗を検出可能にするための規約。

### 1. 名前に主張を入れない

名前は**話題**、主張は**本文**。名前に主張を入れると、本文だけ直しても嘘が残り、
想起 (名前と description を見る) が誤読を生む。

- ✗ `<対象>-not-in-service` / `<対象>-is-broken` / `<対象>-only`
- ○ `<対象>-status` / `<対象>-behavior`

### 2. 種別を書き、腐るものにだけ確認手段を付ける

本文の先頭に置く。frontmatter はホストのスキーマなので勝手に増やさない。

```
**種別:** 現況 (必ず腐る)
**確認:** <真偽を確かめる 1 行のコマンドか手順>
**失効:** <これが起きたら偽になる>
```

| 種別 | 例 | 確認・失効 |
|---|---|---|
| **不変** | ツールの性質、言語の意味論、運用方針 | 不要 |
| **構造** | アーキテクチャ、正本の所在、API 契約 | 確認のみ (リポジトリで見られることが多い) |
| **現況** | いま壊れている / いまこうなっている | **両方必須** |
| **決定** | 「◯◯はやらないと決めた」 | 失効条件 (覆る条件) を書く |

**過剰に付けない。** 不変に確認手段は要らないし、要求すると規約ごと守られなくなる。

### 3. 結論と理由を分けて書く

結論が合っていても理由が古いと、別の事故になる。
「無いから使えない」と書いたが実際は「あるが設定で無効」だった場合、
理由を信じた側は既にあるものを探して混乱する。

### 4. 確かめられることは、そもそもメモリに書かない

リポジトリを見れば分かる事実を書くと、**陳腐化するキャッシュ**になる。
書くのは「見ても分からないこと」だけ。

### 5. inbox から知識への昇格は自動化しない

「この失敗から何が一般化するか」は変換ではなく判断。自動化ではなく判断を安くする。

### 6. この規約自体を書くときも、案件名を書かない

`~/.claude/` は公開 dotfiles で管理されている。
具体例が要るときは `<対象>` のような伏せ字にする。

## 横断知識 (failures.md)

繰り返し踏んだ失敗を、リポジトリを越えて持ち回るための手書きの知識ファイル。

- `~/.local/share/ark/context/knowledge/failures.md` — **作業開始前と、失敗して再試行する前に読む**
- `~/.local/share/ark/context/knowledge/failures-inbox.md` — 再発しそうな失敗の候補を書く先

**inbox から failures.md への昇格は自動化しない。**「この失敗から何が一般化するか」は
変換ではなく判断なので、人間が選んで 1 項目に落とす。

## 開発ワークフロー (gstack + CE/superpowers)

gstackとCE (superpowers) を併用する。それぞれの得意領域で使い分ける。

### gstack を使う場面
- `/office-hours` — アイデアの初期検証 (ビジネス・プロダクト視点)
- `/plan-ceo-review` — プロダクト判断・ビジネスレンズ
- `/plan-eng-review` — アーキテクチャのロック
- `/qa` — Playwright による自動QAテスト
- `/retro` — 週次統計・振り返り
- `/browse` — ヘッドレスブラウザ操作 (Webブラウジングには常にこれを使う)
- `/ship` — リリース・PR作成
- `/cso` — セキュリティ監査

### CE (superpowers) を使う場面
- `brainstorming` — 技術設計のSocratic対話
- `writing-plans` — 2-5分単位のタスク分割による実装計画
- `subagent-driven-development` — 並列エージェントでの高速実装
- `requesting-code-review` — 14エージェント並列コードレビュー
- `test-driven-development` — RED-GREEN-REFACTORサイクル
- `finishing-a-development-branch` — マージ/PR判定

### 統合フロー (推奨)
1. `/office-hours` (gstack) → アイデア検証
2. `/plan-ceo-review` + `/plan-eng-review` (gstack) → ビジネス＆アーキテクチャ承認
3. `brainstorming` (CE) → 技術設計の深掘り
4. `writing-plans` (CE) → 実装計画
5. `subagent-driven-development` (CE) → 実装
6. レビュー: 軽量は `/review` (gstack)、重要は `requesting-code-review` (CE)
7. `/qa` (gstack) → 自動QA
8. `/ship` (gstack) → リリース
